## 4. 実装中に「この要件は成立しない」と判断した箇所

発注書 §6 の指示に従い、読み替えずに記録する。

### 4-1. 媒体の仕様変更に端末の買い替えを含める案

当初 `spec/design.md` §2.2 は「アプリのUI刷新＋端末の買い替え」を1回の変更としてまとめる予定だった。
実装に入って、これが §2-5 の「ファイルの連番（撮影順に単調増加）」と両立しないと分かった。
端末が変われば連番はリセットされ、単調増加が切れる。

→ 読み替えず、**端末を据え置き**にして変更をアプリ側（UI・アカウントID）だけに限定した。
結果、連番は 0412 → 4390 で8年間連続し、ステータスバーは12枚を通して同形のまま残る。

### 4-2. 1画面1投稿では縦糸が主題になってしまう問題

本体10枚に対し、縦糸を年1回・8年ぶん入れると本体の6割が軍手になる。
「年に1回程度の反復」ではなく「軍手の作品」になってしまい、§2-3 と §2-4 が同時に壊れる。

→ 1画面を「ひと月ぶんの投稿一覧（4件）」に変更。本体10枚で投稿40件、縦糸は40件中5件。
残り38件が §2-4 の「統計的な最頻値」を担う。

### 4-3. 2020年（および2011年）を避けられない問題

高2の春から8年という枠に実在の暦を当てると、2012年以降のどの窓も2020年を含み、
それ以前に下げると2011年に当たる。「大きな出来事を作らない」という指示は守れるが、
**作っていない出来事が外から入ってくる**ことは避けられない。

→ 成立しないと判断し、代替案として 2015-2023 を採り、2020年は端末層の変化
（自宅・平日昼・Wi-Fi・充電中・電池100%）としてのみ現れる形にした。本文では一切触れない。
残る穴は README §5-4 に明記した。

## 6. レンダリングのやり直し

| 回 | 事象 | 対処 |
|---|---|---|
| 1 | v2（暗色）の 08・09 が 844px を 37px 溢れた | 写真高さ 104→88px、カード余白 9→7px、月ラベル padding を詰めた |
| 2 | 終端のDM画面で吹き出しが上詰めになっていた | 実際のメッセージ画面と同じく `justify-content: flex-end` で下詰めに |

溢れは目視ではなく、Playwright で `body.scrollHeight` を実測して `output/manifest.json` に残し、
テスト E3 が機械的に検査している。`.device` を `height` ではなく `min-height` にしてあるのは、
中身が溢れたときに body が伸びて検出可能になるようにするため。

```
復旧後                  → 58 passed
```
