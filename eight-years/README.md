# 八年

女子高校生の高校二年から8年間（2015-04 〜 2023-03）の、架空の人生。
架空の記録アプリ「ヌイシロ」に残った12枚のスクリーンショットとして提示する。

```
eight-years/
├── output/        12枚の png（01 が冒頭、02〜11 が本体、12 が終端）＋ manifest.json
├── src/           record.json（単一の真実）／ HTML+CSS 生成 ／ Playwright 撮影
├── spec/          design.md（設計書）・verification.md（検証設計）※実装前に書いた
├── tests/         58件
├── LOG.md         実行ログ
└── README.md      これ
```

再現手順:

```bash
cd eight-years
pip install playwright pytest      # Chromium は /opt/pw-browsers に既存
python3 src/shoot.py               # src/build/*.html → output/*.png
python3 -m pytest tests -q
```

**配置について。** 発注書の表は成果物をリポジトリ直下に置くよう指していますが、直下にはすでに
meeTai 本体の `README.md` と、`pytest.ini` の `testpaths` が指す `tests/` があります。
そのまま置くと両方を破壊するため、内部構成はそのままに `eight-years/` へ丸ごと収めました。
未達項目として §5 にも再掲します。

## 1. 縦糸に何を選んだか。なぜそれを選んだか

**落ちている片方だけの軍手を見つけて撮ること。**

条件は「年に1回程度」「集団的に典型でない」「その人物にとってだけ反復する」の3つでした。
候補を潰していくと、次の3方向がいずれも失格になります。

- 桜・初詣・誕生日のような年中行事 — 発注書が名指しで禁じているだけでなく、
  そもそも「反復している」のが本人ではなく暦のほうなので、8年を貫く糸になりません。
- 特定の場所に結びつくもの（非常階段のひび、同じ席から見える窓） — 本人が引っ越すと
  途切れます。途切れた理由が引っ越しになってしまい、§2-4 の「節目を描かない」と衝突します。
- 形見や記念品 — 意味が最初から確定していて、感情の器になってしまいます。

軍手はこの3つをすべて外します。季節に紐づかず（工事は通年ある）、場所にも紐づかず、
持ち物でもない。ただ落ちている。統計的には日本中でありふれた物で、
反復しているのは軍手ではなく **「それを見つけて撮る」という本人の癖のほう** です。
だから引っ越しても進学しても続くし、続かなかった年があっても理由を要しません。

意味は画面上で一度も説明されません。8年で5回、写真と数語だけが並びます。

## 2. 欠落を何回置いたか。それぞれの理由

**3回。** 年度は4月始まりで数えています。

| 年度 | 縦糸 | 言及 |
|---|---|---|
| 2015 | ○ 2015-05-21 | |
| 2016 | ○ 2016-10-19 | |
| **2017** | **×** | なし |
| 2018 | ○ 2018-09-20 | |
| 2019 | ○ 2019-12-18 | |
| **2020** | **×** | なし |
| **2021** | **×** | あり（2021-05-19「一年くらい軍手を見てない」） |
| 2022 | ○ 2022-08-11 | |

### 年度2017 — 言及なし

高校を出た年です。この年の画面（S05・S06）は投稿時刻が始発の時間帯と深夜に寄り、
平日昼の投稿が消え、自宅でも通信が `wifi` から `mobile` に変わっています。
生活の側が全部入れ替わっているので、癖のひとつが止まったことに本人が気づきません。
**気づかれない欠落**として置きました。

### 年度2020 — 言及なし

外に出ていない年です。画面（S09）は4件とも `context: home`、平日の昼、Wi-Fi、
電池100%の充電中。落ちている物を見つけるには外を歩く必要があるので、
この欠落は行動から自動的に出てきます。理由が端末層に書いてあるぶん、
本人が言葉にする必要がありません。**条件から導かれる欠落**です。

### 年度2021 — 言及あり（1回だけ）

引っ越した年です。ここでだけ本人が「一年くらい軍手を見てない」と書きます。
言及を最後の欠落に置いたのは、順番に意味があるためです。
気づかない → 気づく理由がない → やっと気づく、の順に並べると、
言及が「久しぶりに自分の癖を思い出した」という一回きりの出来事になります。
逆順に並べると、以降の欠落がすべて「まだ見てないやつ」として読まれてしまい、
沈黙している2回が沈黙でなくなります。

なお、欠落が「記録が残っていないだけ」に見えないよう、
**8年度すべてに最低1画面ある**ことをテストで固定しています（C5）。
記録がある年に軍手がない、という形でしか欠落は成立しません。

終端（S12）にも軍手が出ますが、これは相手から送られてきたもので、
本人の縦糸としては数えていません（C7）。

## 3. 検証項目をどう決めたか。何を検証しないと判断したか

詳細は `spec/verification.md`（実装前に書いたもの）にあります。要点だけ。

### 決め方

この成果物の強度は文章の巧拙ではなく、**層と層が食い違っていないこと**にあると考えました。
層は4つあります。

1. **暦** — 日付と曜日、年度の区切り
2. **記録** — 投稿の順序、時刻、本文
3. **端末** — スクショ時刻、電池、通信、ファイル連番
4. **構成** — 冒頭が1枚、仕様変更が1回、縦糸の出現と欠落、終端の話者

「壊れている」を **2つ以上の層が互いに矛盾している状態** と定義しました。
そうすると、機械化できるのは常に **層の中身の当否ではなく、層と層の関係** だと分かります。
「2015-05-21 が木曜であること」は暦と記録の関係なので検査できる。
「その日に軍手が落ちていたのが自然か」は関係ではないので検査できない。

この線引きで 58 件のテストになりました（A: 暦・数値 / B: 端末と行動 / C: 縦糸 / D: 構成と禁止事項 / E: 成果物 / F: 変異）。

### 「電池と通信が行動と整合する」の扱い

発注書の §2-5 で唯一、常識に頼りそうになった項目です。
常識のままだと検査できないので、**規約として明文化**しました（`spec/design.md` §5.3 の R1〜R12）。
「外で充電しない」「Wi-Fi は自宅と職場にしかない」「深夜は家にいる」「夜まで出歩いた日の電池は55%以下」
「朝の非充電時は60%以上」など12条です。常識だから正しいのではなく、
**この作品が宣言したから検査できる**、という立場を取りました。

### 検証しないと決めたもの

- **「大きな出来事を作らない」が守れているか** — 何が「大きい」かは分布の問題で、
  テキストからは判定できません。設計段階で禁じ手（進学・就職・引っ越し・別れ）を
  列挙し、投稿1件ずつ人手で通しました。
- **節目が「周辺の変化としてのみ」現れているか** — 「進学した」と書いていないことは
  検査できますが、「時刻分布の変化として現れている」ことは検査できません。
  変化の指標を `spec/design.md` §4 の表に固定し、目視で確認しています。
- **縦糸が「その人物にとってだけ反復する」ものか** — 典型語ブラックリスト（C6）は
  否定側しか検査できません。肯定側は判定不能なので、選定理由を §1 に書いて委ねます。
- **文章の自然さ・感情の温度** — 主観です。感動的語彙のブラックリスト（D8）で下限だけ守り、
  上限は人手にしました。
- **写真プレースホルダの見た目と、本文との対応** — 発注書が「写真の中身ではなく画面の構造」と
  指示しているので、内容は対象外としました。矩形が存在することだけ確認しています。
- **実在の人物・アカウントとの偶然の一致** — 全網羅は不可能です。アプリ名は検索で確認し、
  表示名はひらがな2文字の愛称に限定、`@英数字` 形式のハンドルを避けて
  架空アプリ内部の数値ID（`ID 4417-08` / `@8261-30`）にしました。

### テストが弱くないことの確認

58件が初回から全部通ったので、`tests/test_mutation.py` に
**意図的に壊した入力を18種類**注入し、対応する検査が確かに違反を報告することを確かめました
（曜日をずらす、スクショを記録より前にする、外出中に充電する、縦糸を全年度に置く、
終端に本人の発話を足す、実在の企業名を混ぜる、など）。18件すべて検出されます。

成果物の層（output/*.png）は変異テストの対象外なので、手で3種類壊して確認しました。
PNGを1枚消す → E1が落ちる。別寸法のPNGに差し替える → E2が落ちる。
manifest に溢れを立てる → E3が落ちる。いずれも検出され、復旧後に58件へ戻ります（`LOG.md` §7）。

## 4. 実装中に方針を変えた箇所と、その理由

### 4-1. 1画面 = 1投稿 → 1画面 = ひと月ぶんの投稿一覧（4件）

当初は1画面に1投稿を置く設計でした。しかし本体は10枚しかなく、
縦糸を年1回・8年ぶん入れると **本体の6割が軍手の画面** になります。
縦糸が支配的になって「反復」ではなく「主題」になってしまう。

画面をプロフィールの投稿一覧（ひと月ぶん、4件）に変えました。
本体10枚で投稿40件になり、縦糸は40件中5件です。
埋め草の38件が §2-4 の「統計的な最頻値」を担うので、要件が2つ同時に片づきました。

### 4-2. タイムラインを「古い順」にするため、UI にトグルを置いた

投稿一覧は普通「新しい順」です。しかしそれだと画面内で時間が逆行し、
画面をまたぐと順行するという、読み手に無用な負荷のかかる構造になります。
かといって説明を足すと §2-1 の「冒頭以外に地の文を置かない」に触れます。

アプリ側に「新しい順 / 古い順」の並び替えを持たせ、本人が常に「古い順」を選んでいることにしました。
トグルの状態が画面に映っているので、説明が要りません。
テスト（A3）は「表示が古い順なら記録も昇順」という形で、UIと配列の一致を検査しています。

### 4-3. 媒体の仕様変更から、端末の買い替えを外した

当初は「アプリのUI刷新 ＋ 端末の買い替え（ステータスバーも変わる）」を1回の変更として
まとめる案でした。実装中に、これが §2-5 の
**「ファイルの連番（撮影順に単調増加）」と両立しない**ことに気づきました。
端末が変われば連番はリセットされます。

端末は据え置き、変わるのは **アプリのUIとアカウントIDだけ** にしました。
結果として連番は 0412 → 4390 まで8年間連続し、
ステータスバーだけが12枚を通して同じ形で残ります。仕様変更をまたいで変わらないものがある、
というのは元の案より良い形だったと思います。

### 4-4. 欠落への言及の置き場所を、2022-02 から 2021-05 に移した

最初は言及を 2022-02（年度2021）に置いていました。ところが本体10枚の割り当てを組むと、
年度2022 の縦糸（2022-08）を入れる画面が足りなくなります。
言及を 2021-05 に移し、S11 を 2022-08 の縦糸にあてました。
結果的に §2 で書いたとおり「気づかない → 気づく理由がない → 気づく」の順になり、
移した後のほうが筋が通っています。

### 4-5. 年代の選び方

高2の春から8年という枠に、実在の暦を当てる必要がありました。
2012年以降のどの8年窓も2020年を含み、それ以前に下げると2011年に当たります。
どちらも「作らないはずの大きな出来事」が外側から入ってきます。

2015-2023 を選び、2020年は **端末層の変化としてのみ** 現れるようにしました。
S09 は4件とも自宅・平日の昼・Wi-Fi・電池100%の充電中で、本文は
置き配、洗濯、屋根、保冷剤しか言いません。世界の側は一度も画面に映りません。
§2-4 が要求する「節目は周辺の変化としてのみ現れる」という技法を、
自分で作った節目ではなく暦そのものに対して使った形です。
ただしこれは読者が外部の文脈を持ち込む余地を残します（§5 に再掲）。

### 4-6. レイアウトの手直し2件

- v2（暗色）の画面が 844px を 37px 溢れていました（08・09）。
  写真の高さを 104px → 88px、カード余白と月ラベルを詰めて解消。
  溢れは Playwright で `body.scrollHeight` を実測して `manifest.json` に残し、
  テスト E3 で機械的に検査しています。
- 終端のDM画面で吹き出しが上詰めになっていました。実際のメッセージ画面は
  入力欄の上に下詰めされるので、`justify-content: flex-end` に変更。

## 5. 要件を満たさなかった箇所

空欄にはできませんでした。以下5件あります。

### 5-1. 成果物をリポジトリ直下に置いていない（意図的）

発注書 §1 の表は `output/` `src/` `spec/` `tests/` `README.md` を直下に置く形です。
このリポジトリの直下には既に meeTai 本体の `README.md` と、`pytest.ini` の
`testpaths = tests` が指す `tests/`（既存のpytestスイート）があり、そのまま置くと両方を壊します。
内部構成は指定どおりのまま、`eight-years/` の下に収めました。

### 5-2. 記録が8年間の端から端までを覆っていない

記録の断片は 2015-05-07 から 2023-03-05 までで、実質7年10ヶ月です。
枠（2015-04 〜 2023-03）には収まっていますが、最初の月と最後の月が空いています。
本体10枚という枚数で年度ごとの分布を優先した結果で、
「高校二年の4月」と「8年目の3月」そのものは画面にありません。

### 5-3. 欠落が「見つけなかった」ことの証明にはなっていない

各年度に最低1画面あることは保証していますが（C5）、1年度あたり画面は1〜2枚、
投稿は4〜8件です。この密度では、ある年に軍手を「見つけなかった」のか
「見つけたが記録に残らなかった」のかを原理的に区別できません。
欠落は、記録がある年に軍手の投稿がない、という形でしか成立していません。
記録媒体という形式を選んだ以上、これは残る穴だと考えています。

### 5-4. 2020年について、読者の外部知識を遮断できていない

§4-5 のとおり、実在の暦に合わせる以上どの8年窓も2020年か2011年を含みます。
作品は一切それに触れませんが、S09（自宅・昼・充電中・Wi-Fi）を見た読者が
外側の文脈を持ち込むことは止められません。
「大きな出来事を作らない」という指示には従っていますが、
**作らなかった出来事が読み込まれる余地**は消せていません。

### 5-5. 固有名詞の非衝突を保証しきれていない

アプリ名「ヌイシロ」は検索し、アプリ・企業・商標いずれにも該当がないことを確認しました
（候補だった「フチドリ」は同名のタイル業者がいたため却下。`LOG.md` §2）。
一方、表示名の「あお」「なつ」はひらがな2文字の愛称で、
実在の誰かの愛称と一致する可能性は排除できません。
氏名・実在SNSのハンドル形式・地名・施設名・企業名は使わず、
アカウント表記も架空アプリ内部の数値IDにしていますが、
「衝突しないことの証明」ではなく「衝突しにくくする措置」にとどまります。

### 参考: 満たしていると判断した項目

冒頭1枚 / 本体10枚 / 終端1枚の構成、冒頭以外に地の文がないこと、
媒体の仕様変更が8年で1回であること、終端が本人以外の発話で閉じ本人の応答がないこと
（既読だけが残る）、終端の後に何も置いていないこと、
数値層（日時・スクショ日時・曜日・端末状態・ファイル連番）の整合、
画像生成APIを使っていないこと — これらはテストで固定しています。
