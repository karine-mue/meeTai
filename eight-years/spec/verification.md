# 検証設計（実装前）

`spec/design.md` と同時に、実装着手前に書いた。

---

## 1. この成果物において「整合が壊れている」とはどういう状態か

この成果物は「実在しない8年間」を、**画面という物証の形で**提示する。
物証としての強度は、文章の巧拙ではなく **層と層の食い違いの無さ** に依存する。層は4つある。

1. **暦の層** — 日付と曜日、年度の区切り
2. **記録の層** — 投稿の順序、時刻、本文の内容
3. **端末の層** — スクリーンショット時刻、電池、通信、ファイル連番
4. **構成の層** — 冒頭が1枚だけであること、媒体の仕様変更が1回であること、縦糸の出現と欠落、終端の話者

「整合が壊れている」とは、これらのうち **2つ以上の層が互いに矛盾する** 状態を指す。具体的には：

- **暦との矛盾**: 2015-05-21 に「水」と書いてある。実在の暦は木曜である。
- **因果の逆転**: 記録より前にスクリーンショットが撮られている。
- **順序の破れ**: 「古い順」と表示しているのに投稿が降順に並ぶ。画面をまたいで時刻が戻る。ファイル連番が撮影順に対して減る。
- **身体との矛盾**: 通学中の電車内で自宅Wi-Fiに繋がっている。外を歩きながら充電されている。深夜3時に学校にいる。一日出歩いた末の21時に電池が96%ある。
- **構成の破れ**: 作者の言葉が冒頭以外に出る。媒体の仕様が0回または2回以上変わる。縦糸が全年度に存在する（=欠落が消える）。欠落への言及が2回以上ある。終端に本人の発話がある。終端の後に何かが続く。
- **世界の混入**: 実在の企業名・施設名・路線名が画面に映る。感動的な語彙で締める。

逆に言えば、**壊れていない**とは、どの層から読み始めても同じ8年間に到達する状態である。

## 2. 機械的に検出できる項目

`src/validate.py` に純粋関数として実装し、`tests/` から呼ぶ。すべて `record.json`（単一の真実）に対して働く。

### A. 暦・数値層 — `tests/test_numeric_layer.py`

| ID | 検査 |
|---|---|
| A1 | 全投稿・全メッセージ・全スクリーンショットの曜日が、実カレンダー（`datetime`）と一致する |
| A2 | 画面内の全記録の日時 < その画面の `shot_at`（因果） |
| A3 | 画面内の記録が時系列昇順（表示中の並び替え「古い順」と一致） |
| A4 | 画面間で `shot_at` が厳密に昇順。かつ 画面Nの最新記録 < 画面N+1の最古記録（期間が重ならない） |
| A5 | `seq` が撮影順に厳密増加、重複なし。ファイル名の `IMG_%04d` と一致 |
| A6 | ファイル名の先頭連番が画面 index と一致し、01 から連続する |
| A7 | `battery` が 1..100 の整数。`bars` が 0..4 の整数 |
| A8 | 生成されたHTMLのステータスバーに `shot_at` の HH:MM が現れる（レンダラが日時を導出していることの検査） |

### B. 端末状態と行動の整合 — `tests/test_device_state.py`

`spec/design.md` §5.3 の R1〜R12 をそのまま実装する。
投稿は電池・通信を持たないため、投稿に適用するのは R3・R4 のみ。R1・R2・R5〜R12 は `device` に適用する。

このルール群は「常識」ではなく**この作品が宣言した規約**である。
規約として明文化することで初めて機械検査の対象になる、という立場を取る。

### C. 縦糸 — `tests/test_thread.py`

| ID | 検査 |
|---|---|
| C1 | 各年度の縦糸投稿数 ≤ 1（「年に1回程度」） |
| C2 | 8年度のうち縦糸が不在の年度が 2以上（「全ての年に存在してはならない」「欠落を2回以上」） |
| C3 | 縦糸の欠落への言及がちょうど1回 |
| C4 | 言及が置かれた年度が、実際に縦糸不在の年度である |
| C5 | 全8年度に最低1画面存在する（欠落が「記録が無いだけ」に退化していない） |
| C6 | 縦糸の対象語が、集団的に典型な語のリスト（桜・初詣・誕生日・花火・クリスマス・正月・成人式・卒業式・七夕・紅葉）に含まれない |
| C7 | 終端画面の軍手は本人の縦糸として数えない（`author == self` の投稿のみ計上） |

### D. 構成・禁止事項 — `tests/test_form.py`

| ID | 検査 |
|---|---|
| D1 | `kind == "notice"` の画面がちょうど1枚で、それが index 1 |
| D2 | notice 以外の画面が作者テキスト欄（`text`）を持たない |
| D3 | 画面総数 10..12。うち本体（notice と終端を除く）が 10..12 |
| D4 | `ui` が時系列で単調（v1→v2）に **ちょうど1回** 変化する |
| D5 | アカウントIDも同じ位置でちょうど1回変わる |
| D6 | 最終画面が `kind == "dm"`、全メッセージの話者が本人でない、本人の発話が0件 |
| D7 | 最終画面が配列の最後（終端の後に画面がない） |
| D8 | 感動的語彙のブラックリストが本文に出現しない |
| D9 | 実在の企業・サービス・施設・路線名のブラックリストが本文とUI文字列に出現しない |

### E. 成果物 — `tests/test_outputs.py`

| ID | 検査 |
|---|---|
| E1 | `output/*.png` が `record.json` の画面と1:1で対応する |
| E2 | 全PNGが 780×1688 px（PNGヘッダを直接読む。画像ライブラリに依存しない） |
| E3 | `output/manifest.json` に記録された各画面の `scroll_height` が viewport 高さ以下（レイアウトが溢れて切れていない） |

### F. テストが弱くないことの検査 — `tests/test_mutation.py`

**全テストが通った状態は、テストが弱いことの証拠にもなりうる。**
そこで `record.json` のコピーに意図的な破壊を1件ずつ注入し、
**対応する検査が確かに違反を報告すること**を検査する。注入する破壊：

1. 曜日を1日ずらす → A1
2. `shot_at` を最新投稿より前にする → A2
3. 画面内の投稿順を入れ替える → A3
4. 画面の順序を入れ替える → A4
5. `seq` を減少させる → A5
6. `battery` を 140 にする → A7
7. `context: transit` のまま `network: wifi` にする → R7/R8
8. 外出中に `charging: true` にする → R1/R2
9. 深夜の `context` を `out` にする → R3
10. 縦糸を全年度に1つずつ置く → C2
11. 欠落への言及を2回にする → C3
12. 本体画面に作者テキストを足す → D2
13. `ui` を2回変化させる → D4
14. 終端に本人の発話を足す → D6
15. 本文に実在企業名を混ぜる → D9
16. 本文に感動的語彙を混ぜる → D8

## 3. 機械的に検出できない項目と、その扱い

| 検出できないもの | なぜ | どう扱うか |
|---|---|---|
| 「大きな出来事を作らない」が守れているか | 何が「大きい」かは分布の問題であり、テキストからは判定できない | 設計段階で禁じ手を列挙し（§4 の「書かないこと」列）、投稿1件ごとに「これは最頻値か」を人手で通す。README に記録する |
| 縦糸が「その人物にとってだけ反復する」ものか | 典型語ブラックリスト（C6）は否定側しか検査できない。肯定側は判定不能 | ブラックリストで既知の典型を弾き、選定理由を README に明記して読者の判断に委ねる |
| 節目が「周辺の変化としてのみ」現れているか | 「進学した」と書いていないことは検査できるが、「時刻分布の変化として現れている」ことは検査できない | 変化の指標を設計表（§4）に固定し、その指標が実際に record.json 上で動いていることだけを目視確認する。テストにはしない |
| 文章が自然か、感情の温度が適切か | 主観 | ブラックリスト（D8）で下限だけ守る。上限は人手 |
| 画面が視覚的に破綻していないか | レンダリング結果の意味は検査できない | 寸法（E2）と溢れ（E3）のみ機械化。配色・字詰め・重なりは生成後に全12枚を目視する |
| 実在の人物・アカウントとの偶然の一致 | 全網羅は不可能 | アプリ名・表示名について一般的な検索を行い、結果を README に残す。表示名はひらがな2文字の愛称に限定し、氏名・handle 形式（`@英数字`）を避け、アカウント表記を架空アプリ内部の数値ID形式にする |
| 8年間が「一人の人物」として読めるか | 判定不能 | 検証しない。設計の責任とする |

### 検証しないと決めたもの

- **本文の日本語としての正しさ**（形態素解析等）: 断片的な口語であることが仕様なので、正しさの基準が立たない。
- **写真プレースホルダの見た目**: 「写真の中身ではなく画面の構造」という発注の指示に従い、内容は検査対象外。矩形が存在することだけ確認する。
- **投稿本文と写真の対応**: 写真がプレースホルダである以上、対応の検査は無意味。

## 4. 通し方

1. `record.json` の日時・曜日は **手で書く**。`datetime` から導出しない。
   導出してしまうと A1 が恒真になり、検査の意味が消えるため。
2. `pytest` を回し、落ちたものを直す。直した内容は `LOG.md` に残す。
3. 全件通ったら `tests/test_mutation.py` を回し、16件の破壊がすべて検出されることを確認する。
4. 生成された12枚を目視し、§3 の「人手で」と書いた項目を通す。
